# Сетевая производительность

Замер 2026-10-05 на облачной функции `gallery` (8 карточек ленты, `curl`):

| | До | После (ожидаемо) |
|---|---|---|
| Ответ `feed`, 8 карточек | 621 КБ (606 КБ gzip): превью base64 внутри JSON | ≈3 КБ (≈1 КБ gzip) |
| TTFB, тёплая функция | 0,85–0,97 с | быстрее: база не читает и не передаёт блобы |
| Холодный старт | 3,9 с | не меняется (платформа); клиент повторяет запрос один раз |
| Веб, первая загрузка | 2 запроса (лента + «работа недели») | 1 пакетный запрос |
| hero-картинка веба | 1,87 МБ PNG | 120 КБ JPEG |

Главная причина задержек: каждая карточка везла 40–140 КБ PNG в `base64`, который не сжимается, а ответ ещё и выбирался из БД целиком. На телефоне к этому добавлялись новое TLS-соединение на каждый запрос и полная перекодировка всех картинок до показа первой карточки.

## Контракт API (обратно совместим)

- `feed` и `work` принимают `lite: true`. Вместо `revision.preview` приходит `revision.has_preview`, блоб из БД не читается. Без флага ответ прежний.
- `GET …/gallery/preview/<revision_id>` (Edge Function) и `GET /api/preview/<revision_id>` (локальный сервер) отдают байты изображения: `Cache-Control: public, max-age=31536000, immutable`, `ETag` = id ревизии, `304` по `If-None-Match`. Ревизия неизменна, поэтому кэш вечный.
- `batch`: `{requests:[{action,payload}…]}` (до 8, только чтение: `feed`, `work`, `profile`, `package`) → `{results:[{data}|{error}]}`.
- `package` больше не содержит превью (`preview: null`), отдаётся с `immutable` и `ETag`.
- Публичная лента (без входа, режимы `new`/`curated`) кэшируется на сервере на 10 с; публикация и модерация сбрасывают кэш. Токен пользователя проверяется в Edge Function не чаще раза в 30 с.
- Локальный сервер: gzip/brotli, `ETag`/`304`, `immutable` для `/assets/*`, `no-cache` для `index.html`.

## Кэширование клиентов

**Android (полное):**
- лента: первая страница на диске, показывается мгновенно (и офлайн); если ей меньше 30 с — сеть не трогаем; если ответ сервера совпал по хэшу — список не перерисовывается;
- превью: память 24 МБ → диск 64 МБ (уменьшены до 480 px, WebP) → одна загрузка на ревизию; грузятся лениво по мере показа карточек, 3 потока;
- пакет шейдера: диск, ключ — id ревизии, хэш кода проверяется при каждом чтении; «пакет + детали работы» одним запросом `batch`;
- детали работы: показываются из кэша, затем обновляются;
- соединения не закрываются после ответа (keep-alive), чтение повторяется один раз при сетевой ошибке или 5xx.

**Веб (лёгкое):** общий in-flight для одинаковых запросов, память 30 с для публичной ленты (сбрасывается любой записью), превью — обычные `<img>` с вечным HTTP-кэшем браузера, первые две карточки с высоким приоритетом, `qrcode` подгружается по клику.

## Выкладка

Клиенты работают и со старой функцией (получат прежние ответы и пакетный запрос заменят параллельными), но выигрыш появляется после деплоя функции:

```
supabase functions deploy gallery
```

Веб выкладывается обычным workflow GitHub Pages, Android — новой сборкой.
